# هدايا همّار × ALM

حملة واحدة بسقف قابل للتعديل (الافتراضي 100 مستفيد)، واختيار عشوائي عند معاينة رسالة طلب مدفوع، أو منح يدوي لطلب محدد. لا ترسل الإضافة الرسائل تلقائيًا؛ تظل المراجعة والإرسال عبر زر واتساب.

## الاستخدام

1. ادخل بحساب يحمل custom claim بقيمة role: admin، ثم افتح /admin/alm من بطاقة «هدايا كوفي ALM» في الإدارة.
2. حدد الحد الأعلى للمستفيدين ووصف الهدية ونسبة الاختيار. فعّل الاختيار العشوائي واحفظ.
3. عند معاينة رسالة واتساب لطلب مدفوع من حساب الأدمن، يفحص الخادم الطلب مرة واحدة. إذا اختير، يُضاف رابط بطاقة QR إلى النص.
4. للمنح اليدوي، أدخل رقم الطلب الكامل في لوحة الهدايا، أو اضغط «منح هدية ALM لهذا الطلب» في إجراءات الطلب.
5. يفتح العميل الرابط /alm/gift/[token] ويعرض QR في ALM، ويمكنه حفظ صورة الكود، دون حساب.
6. يمسح الأدمن QR بكاميرا الهاتف. يفتح /admin/alm/redeem/[token]، ويعود إليه بعد تسجيل الدخول. يمكن أيضًا لصق رابط الهدية في اللوحة.
7. يعاين الأدمن التفاصيل ويحدد خانة التأكيد ثم يضغط «تأكيد الاستخدام وتحضير الطلب». المسح التالي يوضح أن الكود استُخدم ولا يطلب تحضير طلب آخر.

فتح الرابط وطلبات GET لا تستهلك الهدية. الصرف يسجل عند تأكيد الأدمن فقط.

## قواعد الاختيار

- الحد يشمل اليدوي والعشوائي معًا. مستفيد واحد لكل رقم هاتف مُوحّد، حتى لو طلب أكثر من مرة.
- المستفيد هو **صاحب الطلب/الدافع**. في طلب الإهداء، تصل هدية ALM إلى المرسل؛ تظل بيانات مستلم العطر مستقلة.
- النسبة احتمال لكل طلب مؤهل، وليست وعدًا باكتمال السقف خلال عدد محدد من الطلبات. 100% تمنح كل عميل مؤهل حتى اكتمال العدد.
- قرار عدم الفوز يُحفظ؛ إعادة المعاينة أو تغيير النسبة لا يعيدان السحب للطلب نفسه. يمكن للأدمن تجاوزه بمنح يدوي ضمن السقف.
- الطلبات التي لم تُفحص بسبب إيقاف العشوائي أو اكتمال السقف يمكن فحصها لاحقًا عند التفعيل أو رفع السقف.
- تكرار المعاينة أو المنح يعيد القسيمة نفسها ولا يزيد العداد.
- تبدأ الحملة والعشوائي متوقف. لا يوجد زر لتصفير السجل أو إعادة فتح قسيمة مستعملة.
- إيقاف العشوائي لا يلغي القسائم السابقة ولا يمنع المنح اليدوي.
- تغيير وصف الهدية يطبق على القسائم الجديدة فقط.
- يُفحص دفع الطلب وعدم إلغائه/استرجاعه عند المنح والعرض والصرف. قراءة الطلب تتم من قاعدة المتجر قبل معاملة الصرف في القاعدة الخاصة؛ لا توجد معاملة موزعة بين القاعدتين.

## التفعيل على الاستضافة

الميزة **غير مفعلة افتراضيًا**. لم تُنشأ موارد أو تُنشر قواعد أو تُغيّر بيانات المتجر تلقائيًا.

### قاعدة الهدايا الخاصة

أنشئ قاعدة Cloud Firestore Standard / Native مسماة **alm-rewards** داخل مشروع Firebase الحالي **devana-digital**، ويفضل في منطقة قاعدة المتجر نفسها.

تستمر الطلبات في قاعدة (default). تُحفظ الحملة والقرارات والقسائم والصرف في alm-rewards. يمنع الكود استخدام (default) كسجل للهدايا، لتجنب الاعتماد على قواعد المتجر غير الموجودة في المستودع.

طبّق ملف **firestore.alm.rules** على قاعدة الهدايا فقط. يمنع كل وصول مباشر من المتصفح حتى للحسابات المسجلة. الخادم يستخدم Admin SDK، ويتحقق من صلاحية الأدمن في API.

بعد إنشاء القاعدة، انشر القواعد عبر Firebase CLI:

~~~bash
firebase deploy --only firestore --config firebase.alm.json --project devana-digital
~~~

ملف firebase.alm.json يستهدف alm-rewards فقط. **لا تطبق ملف المنع على قاعدة الطلبات الافتراضية.**

### صلاحيات الخادم

أضف القيم عبر إدارة أسرار الاستضافة، دون إدراج المفاتيح في Git:

~~~dotenv
FIREBASE_PROJECT_ID=devana-digital
ALM_FIRESTORE_DATABASE_ID=alm-rewards
FIREBASE_SERVICE_ACCOUNT_JSON=<one-line service account JSON>
SITE_URL=https://hammar1.shop
ALM_REWARDS_ENABLED=true
~~~

في استضافة Google التي تدعم Application Default Credentials، يمكن استخدام حساب خدمة الاستضافة بدل JSON. يحتاج الخادم إلى قراءة الطلبات والكتابة في قاعدة الهدايا والتحقق من ID tokens بما يشمل إبطال الجلسة.

لا تستخدم بادئة NEXT_PUBLIC_ للمفتاح الخاص، ولا تضبط متغيرات المحاكيات على الإنتاج. في نشر المعاينة، اضبط SITE_URL على نطاق التجربة حتى يفتح QR البيئة نفسها.

### تحقق قبل الإطلاق

- افتح لوحة الهدايا كأدمن واحفظ الإعدادات.
- استخدم طلبًا مدفوعًا تجريبيًا وامنحه هدية يدويًا.
- افتح بطاقة العميل وتحقق أن QR يفتح مسار الصرف في النطاق الصحيح.
- جرب زائرًا وحساب staff؛ لا يمكنهما الصرف.
- أكد الصرف مرة، ثم أعد المسح من هاتف آخر؛ يجب ظهور «تم استخدام هذا الكود سابقًا».
- من عميل Firestore متصفح، تحقق أن قراءة وكتابة قاعدة alm-rewards ترفضان.
- فعّل العشوائي بالنسبة والعدد المطلوبين.

إبقاء ALM_REWARDS_ENABLED=false يترك رسائل الطلبات الحالية تعمل دون سحب أو إضافة هدايا.

## الحماية

- رموز عشوائية بطول 256 بت.
- تحقق خادمي من Firebase ID token عبر verifyIdToken(token, true) ثم role === "admin". دور الموظف لا يكفي.
- إنشاء القسيمة وقرار الطلب ومفتاح العميل وتحديث السقف في معاملة واحدة.
- تسجيل usedAt وusedBy وعداد الصرف في معاملة واحدة. عند مسحين متزامنين تنجح عملية صرف واحدة.
- لا توجد API لإعادة فتح القسيمة أو تصفير العدادات.
- API العميل لا يعرض اسم المشتري أو هاتفه أو رقم طلبه. يُنشأ QR على الخادم بواسطة qrcode دون خدمة صور خارجية.
- ردود API غير مخزنة مؤقتًا. صفحات الهدايا وAPI غير مفهرسة وتستخدم no-referrer.

## الاختبارات

~~~bash
npm ci
npm run test:orders
npm run test:alm
npm run build
~~~

اختبارات السياسة والصلاحيات وإخراج QR لا تتصل ببيانات المتجر. تُتخطى اختبارات معاملات Firestore ما لم يكن المحاكي متاحًا.

شغل Firestore Emulator محليًا ثم:

~~~bash
FIRESTORE_EMULATOR_HOST=127.0.0.1:8085 npm run test:alm
~~~

تستخدم الاختبارات المشروع الثابت demo-hammar-alm-tests فقط، دون مفاتيح إنتاج. تشمل ثبات السحب، التكرار، توحيد رقم الهاتف، السقف المتزامن، مسحين متزامنين، الإلغاء، المنح اليدوي، وعدم تخفيض السقف عن الهدايا الممنوحة.

المراجع: [Firebase Admin setup](https://firebase.google.com/docs/admin/setup)، [ID tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens)، [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions)، [قواعد القواعد المسماة](https://firebase.google.com/docs/firestore/security/rules-structure)، [node-qrcode](https://github.com/soldair/node-qrcode).
